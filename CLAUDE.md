This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working rules

- **Never write or edit code unless the user explicitly asks for it.** Bash commands the user runs themselves (`git switch`, `git pull`, `git status`, creating a branch, etc.) are just them running commands, not requests for work. Do not infer a task from a branch name, session name, or earlier discussion. Acknowledge the output briefly, then wait for an explicit instruction. If the next step seems obvious, offer it in one line and let the user decide.

## Status

Early stage; Auth0 login and user sync (spec `.claude/specs/2_auth0-implementation.md`), the dashboard with course-outline generation (spec `.claude/specs/3_dashboard-ui.md`), lesson content with the lesson page (spec `.claude/specs/5_content-creation.md`), Hinglish audio (spec `.claude/specs/6_hinglish-audio.md`), per-module YouTube videos (spec `.claude/specs/7_module-videos.md`), the PDF download (spec `.claude/specs/8_course-pdf.md`, now per lesson as in the roadmap) and the content gaps of spec `.claude/specs/9_content-gaps.md` (lesson key topics, course tags, further reading, and a create form with only topic and depth) are implemented. `client/` has the marketing landing page (`src/pages/LandingPage.jsx`, routed at `/` in `src/App.jsx`); the navbar has only "Demo" (opens the Warm Cream Demo Video modal, `src/components/LandingModals.jsx`) and "How it works" (links to the static `public/project_working.html`). The hero "Get started for free" calls `handleGetStarted`, which runs `loginWithRedirect` (or goes straight to `/dashboard` if already signed in); Auth0 callback errors show on the landing page. There are no custom login/sign-up forms; Auth0 Universal Login owns all of it.

The app follows the hackathon roadmap (`Hackathon Roadmap.pdf` in the user's `Project-search` folder, outside this repo) and is kept deliberately simple: plain Tailwind, small hooks, native browser controls. `/dashboard`, `/courses/:courseId`, `/courses/:courseId/lessons/:lessonId` and `/courses/:courseId/modules/:moduleId/video` are children of one protected layout route (`src/layouts/DashboardLayout.jsx`, wrapped in `ProtectedRoute`). The layout calls `POST /api/users/sync`, then renders a light-theme page: `components/layout/Sidebar.jsx` (Dashboard link, the course list, and under the open course its modules with "Module video" and the lessons, ✓ when completed; below 768px it is hidden until the top bar's ☰ button opens it, and any link closes it), `components/layout/TopBar.jsx` (user and Log out) and the page via `<Outlet />`. `pages/Dashboard.jsx` is the create form (`components/dashboard/CreateCourseForm.jsx`, topic and depth only) and the course cards (`CourseCard.jsx`, at most 3 tags plus "+n", delete via `window.confirm`). `pages/CoursePage.jsx` is the syllabus (all the course's tags, and each lesson's key topics; both are `components/ChipList.jsx`, which renders nothing for an empty list); after "Generate course" the app goes there. Global state is `src/context/CoursesContext.jsx` (read it with `hooks/useCourses.js`): the course list and the outline of the course in the URL, each with a `refresh…()`; there is no caching and no optimistic update, so a change (complete, delete, create) calls the API and then refreshes. The outline is polled every 3 s while any of its lessons is still being written. Errors are shown inline (`ErrorMessage`); there are no toasts or modals.

Pages fetch their own data with small hooks (`useLesson`, `useLessonAudio`, `useModuleVideo`), all of which poll through `hooks/usePolling.js` (a `setInterval` every 3 s while the server is still working). `LessonPage` and `ModuleVideoPage` render an inner component keyed by `lessonId` / `moduleId`, so each lesson or module starts with fresh state. The lesson page is one plain column: header (objectives, key-topic chips, Download PDF), content, quiz, the Hinglish audio card (on every ready lesson), Further reading (`components/lesson/FurtherReading.jsx`, hidden when there are no readings), then Mark as completed and Previous / Next (`components/lesson/StepNav.jsx`, order from `utils/courseSteps.js`: each module's video, then its lessons). `LessonRenderer` maps block types to components in `components/lesson/blocks/` and skips unknown types; `mcq` blocks are drawn by `Quiz.jsx`. AI text is parsed by `parseInlineText` in `utils/inlineText.js` and rendered by `InlineText` (only `**bold**` and `` `code` ``, never HTML). Hinglish audio uses a native `<audio controls>` and a `<details>` transcript; audio is made on the "Listen in Hinglish" click and the MP3 is fetched as a blob with the bearer token (`apiRequestBlob` in `utils/api.js`), because `<audio src>` can't send it. The module video page is a plain `youtube-nocookie` iframe; "Video not working? Try the next one" calls `report-unavailable`. It never touches progress.

PDF (roadmap milestone 11): `components/lesson/LessonPdfExporter.jsx` downloads one lesson, ending with its further reading (the search phrase is printed, since links in the image-based PDF can't be clicked). It renders `LessonPdfView.jsx` off-screen, captures each of its direct children with `html2canvas` (lazy-loaded, like `jsPDF`), and `utils/pdfLayout.js` (`placeOnPages`, pure and tested) stacks the images on A4 pages, starting a new page when a block doesn't fit. `LessonPdfView.jsx` must stay plain elements with complete inline styles, because `onclone` strips the app's stylesheets from the clone `html2canvas` draws (it can't parse `oklch`, which Tailwind's colors use).

`server/` has the Express API: `GET /api/health`, `POST /api/users/sync`, `GET /api/users/me`, and the course routes under `/api/courses` (list, outline, create/generate, delete, progress `PATCH`, plus `GET /:courseId/lessons/:lessonId`, `POST /:courseId/lessons/:lessonId/retry`, and the Hinglish audio routes `GET|POST /:courseId/lessons/:lessonId/audio` and `GET /:courseId/lessons/:lessonId/audio/file`, and the module video routes `GET|PATCH /:courseId/modules/:moduleId/video` and `POST /:courseId/modules/:moduleId/video/retry|report-unavailable`). Models: `User` (keyed on Auth0 `sub`), `Course` (owns `creator`, `tags` and embedded lesson progress), `Module`, `Lesson`. Course creation calls Gemini for the outline; the lessons are then written in the background (see below). `POST /api/courses` reads only `topic` and `depth` and ignores anything else. `landing_page/` at the repo root is the original standalone AI Studio export the landing page came from, kept for reference and not part of the app. Update this file as the real entry points and conventions land.

## Layout

Two independent npm packages (no root `package.json`, no workspaces). Run npm commands from inside each folder.

- `server/` — Express 5 + Mongoose API, ES modules (`"type": "module"`, so use `import`/`export` and include file extensions in relative imports).
  - Layered folders: `routes/` → `controllers/` → `services/` → `models/`, plus `middlewares/`, `utils/`, `config/`.
  - Auth: `express-oauth2-jwt-bearer` (Auth0-style JWT validation, needs audience and issuer base URL env vars).
  - LLM: `@google/genai` (Gemini) is the course-generation provider. `axios` is for outbound HTTP.
  - Config via `dotenv`: `config/env.js` loads `.env`, checks the seven required vars (`PORT`, `MONGODB_URI`, `AUTH0_ISSUER_BASE_URL`, `AUTH0_AUDIENCE`, `CLIENT_ORIGIN`, `GEMINI_API_KEY`, `GEMINI_MODEL`) and exits if any is missing. `GEMINI_FALLBACK_MODEL`, `LESSON_GEN_CONCURRENCY`, `LESSON_ATTEMPT_TIMEOUT_MS`, `LESSON_TOTAL_TIMEOUT_MS` and the audio settings (`GEMINI_TTS_MODEL`, `GEMINI_TTS_FALLBACK_MODEL`, `GEMINI_TTS_VOICE`, `AUDIO_GEN_CONCURRENCY`, `AUDIO_DAILY_LIMIT_PER_USER`, `AUDIO_TOTAL_TIMEOUT_MS`) and the video settings (`YOUTUBE_API_KEY`, `YOUTUBE_REGION_CODE`, `VIDEO_GEN_CONCURRENCY`, `VIDEO_DAILY_LIMIT_PER_USER`) are optional. `.env.example` exists; never edit `.env`.
  - Every error response is `{ message }`, produced by `middlewares/errorHandler.js` (it shows the message for statuses below 500 and for 502/503/504; other 5xx are generic). `app.js` builds the Express app (importable by tests); `server.js` connects to Mongo and listens.
  - Every course query is filtered by `creator` (the Auth0 `sub`); a course that isn't the caller's is a 404, never a 403. Constants shared with the client live in `utils/courseConstants.js` and must stay identical to `client/src/constants/course.js`.
  - Generation: `services/geminiClient.js` (`generateJson`) is the shared Gemini plumbing for outlines (`services/courseGenerationService.js`) and lessons (`services/lessonGenerationService.js`): up to 3 Gemini attempts (JSON schema) across `GEMINI_MODEL` then the optional `GEMINI_FALLBACK_MODEL`, 40s per attempt and 90s overall (504) for outlines, `LESSON_ATTEMPT_TIMEOUT_MS` (60s) and `LESSON_TOTAL_TIMEOUT_MS` (120s) for lessons. Busy/rate-limited/network failures that exhaust the attempts are a 503; bad or invalid output is a 502; a 400/401/403/404 from Gemini (wrong key or model name) is not retried on that model. Raw upstream messages are only logged, never sent to the client. The outline also gives each lesson `keyTopics` (at most 5, 60 characters each) and the course `tags` (lowercase, at most 6, 30 characters each); `validateOutline` cleans both leniently and they never fail an outline. The lesson prompt is given the lesson's key topics and told to cover them. Courses made before them return empty arrays. A per-user in-memory lock (in `services/courseService.js`) returns 409 for a second concurrent generation; it only works for a single server process.
  - Lessons (`services/lessonQueue.js`): every lesson has a `status` (`pending` → `generating` → `ready` | `failed`). `ensureQueued(courseId)` (called after course creation, on every outline GET and every lesson GET) queues a course's pending lessons in module then lesson order; `prioritize` moves one the user is waiting on to the front; at most `LESSON_GEN_CONCURRENCY` (2) Gemini calls run at once, one lesson per course at a time; claiming is an atomic `findOneAndUpdate`, a failure marks only that lesson `failed` (only the user's Retry re-queues it), and `deleteCourse` calls `cancelCourse`. The queue is in memory, so like the 409 lock it only works for a single server process. `server.js` runs `recoverStaleLessons()` at boot: it gives lessons that predate the `status` field a `pending` status and resets `generating` lessons older than 3 minutes (`ensureQueued` does the same reset per course). Nothing is enqueued at boot. Lesson `content` is an array of typed blocks (see the spec), validated by `validateLessonContent`. Gemini returns separate `explanation` and `quiz` arrays (every explanation-block field is `required` in the schema, because lite models skip optional ones) and `toContent()` merges them into that array; the validator drops empty-body blocks and cuts questions beyond 5, but still needs a paragraph, an example and 4+ valid questions, and the reason for a rejected output is logged (never sent to the client). `lastError`, `videoQuery` and `attempts` are never sent to the client.
  - Further reading (spec 9): Gemini also returns `readings` (`title`, `kind`, `searchQuery`). They are a lesson field, not content blocks, so `LessonRenderer`, the block validator and the audio source hash are unaffected. The AI never writes URLs: `utils/readingUrl.js` builds each link from one fixed Google search template when the lesson is served. `validateReadings` drops empty, over-long, duplicate and URL-like items (anything containing `www.` or `://`; a bare "HTTP" is allowed), maps an unknown kind to `article` and keeps at most 4; a lesson with none is still `ready` (the reason for a drop is logged). Lessons written with readings have `contentVersion` 2; older ones are not back-filled and return `readings: []`.
  - Hinglish audio (spec 6, `services/audio*.js`, `hinglishScriptService.js`, `ttsService.js`): any ready lesson of the caller's own course can request it; there is no per-course switch. `buildAudioSource` turns a ready lesson's blocks into the prompt text (MCQs and `videoQuery` never included); its SHA-256 is the cache key, so `lesson.audio` (`generating` → `ready` | `failed`) stays valid until that text changes, and replays never call Gemini. A job writes the script with `generateJson`, then speaks it with `generateSpeech` in `geminiClient.js` (the Interactions API with `speech_metadata` style annotations, raw 24 kHz L16 PCM; the TTS docs no longer use `generateContent`) in chunks of ≤ 1,800 characters stitched with 400 ms gaps, encodes MP3 in a worker thread (`utils/mp3Worker.js`, `@breezystack/lamejs`) and stores it in the GridFS bucket `lessonAudio`. `services/audioJobs.js` runs jobs in memory (`AUDIO_GEN_CONCURRENCY`, default 1), and the per-user daily limit (429) is counted in memory, so both only work for a single server process. Claiming is an atomic `findOneAndUpdate`; `server.js` marks interrupted jobs `failed` and sweeps orphaned files at boot; `deleteCourse` cancels jobs and deletes the course's files. `fileId`, `sourceHash`, model names and `lastError` are never sent to the client.
  - Module videos (spec 7, `services/moduleVideoService.js`, `videoJobs.js`, `videoLimits.js`, `videoQueryService.js`, `videoRankService.js`, `youtubeClient.js`): `Module.video` is `null` until the first GET claims it atomically and starts a job (`searching` → `ready` | `none` | `failed`); no search runs at course creation, and a GET never restarts `none` or `failed`, only `POST …/retry` does. A job writes a phrase from the outline with `generateJson`, makes one `search.list` call, one `videos.list` call and has Gemini return ordered `approvedIds`; candidates are saved straight after the search and steps resume from what is saved, so Try again never repeats a search that succeeded. `none` allows one Search again (`searchCount < 2`); losing every approved video sets `lostAllVideos`, which reopens one more. A GET on a `ready` video over 7 days old re-checks it in the background and never delays the response. The per-user daily cap (429) and two quota stops (search and details, each until midnight Pacific, both blocking new searches) live in `videoLimits.js`; they and the job runner are in memory, so only work for a single server process. `YOUTUBE_API_KEY` is server-only: never a `VITE_` variable, and axios errors are never logged because their URL contains it. Unapproved candidates, `query`, `searchCount`, `lostAllVideos`, `description`, counts and `lastError` are never sent to the client.
- `client/` — Vite 8 + React 19, JavaScript (JSX, no TypeScript).
  - Styling is **Tailwind CSS v4** only (`@tailwindcss/vite` plugin in `vite.config.js`, `@import "tailwindcss"` in `src/index.css`); there is no component library and no icon package (icons are text characters like ✓ ▶ ☰). The landing page uses its own hard-coded colors and must not change.
  - The app's light palette is defined once in `@theme` in `src/index.css` (`cream`, `ink`, `muted`, `line`, `accent`, `brand`, `success`, so `bg-cream`, `text-muted`, `border-line`…). Use those names, not hex values, in app components. The same file has the shared classes `.card`, `.btn` + `.btn-primary` / `.btn-secondary`, and heading fonts and focus rings scoped to the `.app` wrapper (set by `DashboardLayout`).
  - Routing: `react-router-dom` v7. Auth: `@auth0/auth0-react`, provider in `src/context/Auth0ProviderWithNavigate.jsx` (inside `BrowserRouter`). API calls go through `src/utils/api.js` (`apiRequest`).
  - `html2canvas` + `jspdf` export one lesson to PDF in the browser (see Status).
  - `vite.config.js` proxies `/api` to `http://localhost:5000` in dev.

## Commands

Both packages pin Node 22 (`engines.node: "22.x"`). CI is `.github/workflows/ci.yml` (spec `.claude/specs/10_ci-pipeline.md`): on every pull request into `main` and push to `main`, the `server` job runs `npm ci` and `npm test`, and the `client` job runs `npm ci`, `lint`, `test` and `build`. It reads the Node version from each `package.json`, uses no secrets and does not deploy. Branch protection refers to the job names, so don't rename them.

Client (`cd client`):
- `npm run dev` — Vite dev server
- `npm run build` / `npm run preview`
- `npm run lint` — oxlint (not ESLint). `react/set-state-in-effect` is off in `.oxlintrc.json`: it flags every effect that calls an async loader, even though state is only set after the `await`.
- `npm test` — Vitest with jsdom. Tests are in `client/tests/` and cover the pure helpers (`pdfLayout`, `courseSteps`); how a PDF actually looks needs a check in a real browser.

Server (`cd server`):
- `npm run dev` — `node --watch server.js`; `npm run start` — `node server.js`.
- `npm test` runs Vitest (`vitest.config.js` sets dummy env vars). Tests are in `server/tests/`: supertest against `app.js`, `checkJwt` and the Gemini services mocked (`courses.test.js` and `lessons.test.js` also mock `lessonQueue.js`; `lessonQueue.test.js` runs the real queue with a mocked lesson generator; `audio.test.js` runs the real audio jobs and GridFS with `generateJson` / `generateSpeech` mocked; `moduleVideo.test.js` runs the real video jobs with `generateJson` and `youtubeClient.js` mocked; `youtubeClient.test.js` mocks `axios`), Mongo via `mongodb-memory-server` (the first run downloads a `mongod` binary). Single file: `npx vitest run tests/courses.test.js`; single test: add `-t "name"`.
- `nodemon` was removed (it pulled in a `minimatch` advisory); use `node --watch`.
