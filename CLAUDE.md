# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working rules

- **Never write or edit code unless the user explicitly asks for it.** Bash commands the user runs themselves (`git switch`, `git pull`, `git status`, creating a branch, etc.) are just them running commands, not requests for work. Do not infer a task from a branch name, session name, or earlier discussion. Acknowledge the output briefly, then wait for an explicit instruction. If the next step seems obvious, offer it in one line and let the user decide.

## Status

Early stage; Auth0 login and user sync (spec `.claude/specs/2_auth0-implementation.md`), the dashboard with course-outline generation (spec `.claude/specs/3_dashboard-ui.md`), lesson content with the lesson page (spec `.claude/specs/5_content-creation.md`), Hinglish audio (spec `.claude/specs/6_hinglish-audio.md`) and per-module YouTube videos (spec `.claude/specs/7_module-videos.md`) are implemented. `client/` has the marketing landing page (`src/pages/LandingPage.jsx`, routed at `/` in `src/App.jsx`); the navbar has only "Demo" (opens the Warm Cream Demo Video modal, `src/components/LandingModals.jsx`) and "How it works" (links to the static `public/project_working.html`). The hero "Get started for free" calls `handleGetStarted`, which runs `loginWithRedirect` (or goes straight to `/dashboard` if already signed in); Auth0 callback errors show on the landing page. There are no custom login/sign-up forms; Auth0 Universal Login owns all of it.

The dashboard: `/dashboard`, `/courses/:courseId`, `/courses/:courseId/lessons/:lessonId` and `/courses/:courseId/modules/:moduleId/video` are children of one protected layout route (`src/layouts/DashboardLayout.jsx`, wrapped in `ProtectedRoute`). The layout calls `POST /api/users/sync` once, then mounts Chakra (dark-only) with a course-tree sidebar (a drawer below 768px), a top bar with the user menu, and the page. `pages/Dashboard.jsx` is just the Create Course form and Continue Learning cards; `pages/CoursePlaceholder.jsx` is a stand-in for the course page (`/courses/:courseId`), which is not built yet. After "Generate course" the app goes straight to Lesson 1 (temporary until the course page exists). State lives in `src/context/CoursesContext.jsx` (courses, lazily fetched outlines, a cache of ready lessons, tree expansion, optimistic progress via `setLessonCompleted` / `setCurrentLesson`; read it with `hooks/useCourses.js`). Components are in `src/components/dashboard/`.

The lesson page (`pages/LessonPage.jsx`, data from `hooks/useLesson.js`, components in `src/components/lesson/`): header, collapsible sections from the registry in `lessonSections.js` (Explanation, Quiz, and Hinglish audio, shown only when the course has `options.hinglishAudio`; a later session adds a section with one entry plus one component), and a footer with Mark as completed and Previous / Next. While a lesson is `pending` or `generating` the hook polls every 3 s (paused while the tab is hidden). `LessonRenderer` maps block types to components in `components/lesson/blocks/` and skips unknown types; AI text is parsed by `InlineText` (only `**bold**` and `` `code` ``, never HTML). `HinglishAudioSection` (data from `hooks/useLessonAudio.js`, player and transcript in `components/lesson/audio/`) only reads the audio status when opened; audio is made on the "Listen in Hinglish" click, polled every 3 s while generating, and the MP3 is fetched as a blob with the bearer token (`apiRequestBlob` in `utils/api.js`), because `<audio src>` can't send it.

The module video page (`pages/ModuleVideoPage.jsx`, data from `hooks/useModuleVideo.js`, components in `src/components/video/`) opens from the "Module video" row, the first row of each module in the sidebar (`ModuleVideoTreeItem.jsx`). It isn't a lesson: it never touches progress, the resume point or the lesson counts. `utils/courseSteps.js` is the Previous / Next order (each module's video, then its lessons), rendered by `components/lesson/StepNav.jsx`; "Start Lesson 1" is the video page's Next action. `VideoPlayer` shows a thumbnail and loads YouTube's IFrame API only on click (`utils/youtubeApi.js`); player errors 100/101/150 report the video and move to the next one.

`server/` has the Express API: `GET /api/health`, `POST /api/users/sync`, `GET /api/users/me`, and the course routes under `/api/courses` (list, outline, create/generate, delete, progress `PATCH`, plus `GET /:courseId/lessons/:lessonId`, `POST /:courseId/lessons/:lessonId/retry`, and the Hinglish audio routes `GET|POST /:courseId/lessons/:lessonId/audio` and `GET /:courseId/lessons/:lessonId/audio/file`, and the module video routes `GET|PATCH /:courseId/modules/:moduleId/video` and `POST /:courseId/modules/:moduleId/video/retry|report-unavailable`). Models: `User` (keyed on Auth0 `sub`), `Course` (owns `creator`, options and embedded lesson progress), `Module`, `Lesson`. Course creation calls Gemini for the outline; the lessons are then written in the background (see below). Not built yet: Side Quest and the course PDF (the Side Quest toggle is stored on the course; the outline prompt gets it as context only), and the course page. `landing_page/` at the repo root is the original standalone AI Studio export the landing page came from, kept for reference and not part of the app. Update this file as the real entry points and conventions land.

## Layout

Two independent npm packages (no root `package.json`, no workspaces). Run npm commands from inside each folder.

- `server/` — Express 5 + Mongoose API, ES modules (`"type": "module"`, so use `import`/`export` and include file extensions in relative imports).
  - Layered folders: `routes/` → `controllers/` → `services/` → `models/`, plus `middlewares/`, `utils/`, `config/`.
  - Auth: `express-oauth2-jwt-bearer` (Auth0-style JWT validation, needs audience and issuer base URL env vars).
  - LLM: `@google/genai` (Gemini) is the course-generation provider. `axios` is for outbound HTTP.
  - Config via `dotenv`: `config/env.js` loads `.env`, checks the seven required vars (`PORT`, `MONGODB_URI`, `AUTH0_ISSUER_BASE_URL`, `AUTH0_AUDIENCE`, `CLIENT_ORIGIN`, `GEMINI_API_KEY`, `GEMINI_MODEL`) and exits if any is missing. `GEMINI_FALLBACK_MODEL`, `LESSON_GEN_CONCURRENCY`, `LESSON_ATTEMPT_TIMEOUT_MS`, `LESSON_TOTAL_TIMEOUT_MS` and the audio settings (`GEMINI_TTS_MODEL`, `GEMINI_TTS_FALLBACK_MODEL`, `GEMINI_TTS_VOICE`, `AUDIO_GEN_CONCURRENCY`, `AUDIO_DAILY_LIMIT_PER_USER`, `AUDIO_TOTAL_TIMEOUT_MS`) and the video settings (`YOUTUBE_API_KEY`, `YOUTUBE_REGION_CODE`, `VIDEO_GEN_CONCURRENCY`, `VIDEO_DAILY_LIMIT_PER_USER`) are optional. `.env.example` exists; never edit `.env`.
  - Every error response is `{ message }`, produced by `middlewares/errorHandler.js` (it shows the message for statuses below 500 and for 502/503/504; other 5xx are generic). `app.js` builds the Express app (importable by tests); `server.js` connects to Mongo and listens.
  - Every course query is filtered by `creator` (the Auth0 `sub`); a course that isn't the caller's is a 404, never a 403. Constants shared with the client live in `utils/courseConstants.js` and must stay identical to `client/src/constants/course.js`.
  - Generation: `services/geminiClient.js` (`generateJson`) is the shared Gemini plumbing for outlines (`services/courseGenerationService.js`) and lessons (`services/lessonGenerationService.js`): up to 3 Gemini attempts (JSON schema) across `GEMINI_MODEL` then the optional `GEMINI_FALLBACK_MODEL`, 40s per attempt and 90s overall (504) for outlines, `LESSON_ATTEMPT_TIMEOUT_MS` (60s) and `LESSON_TOTAL_TIMEOUT_MS` (120s) for lessons. Busy/rate-limited/network failures that exhaust the attempts are a 503; bad or invalid output is a 502; a 400/401/403/404 from Gemini (wrong key or model name) is not retried on that model. Raw upstream messages are only logged, never sent to the client. A per-user in-memory lock (in `services/courseService.js`) returns 409 for a second concurrent generation; it only works for a single server process.
  - Lessons (`services/lessonQueue.js`): every lesson has a `status` (`pending` → `generating` → `ready` | `failed`). `ensureQueued(courseId)` (called after course creation, on every outline GET and every lesson GET) queues a course's pending lessons in module then lesson order; `prioritize` moves one the user is waiting on to the front; at most `LESSON_GEN_CONCURRENCY` (2) Gemini calls run at once, one lesson per course at a time; claiming is an atomic `findOneAndUpdate`, a failure marks only that lesson `failed` (only the user's Retry re-queues it), and `deleteCourse` calls `cancelCourse`. The queue is in memory, so like the 409 lock it only works for a single server process. `server.js` runs `recoverStaleLessons()` at boot: it gives lessons that predate the `status` field a `pending` status and resets `generating` lessons older than 3 minutes (`ensureQueued` does the same reset per course). Nothing is enqueued at boot. Lesson `content` is an array of typed blocks (see the spec), validated by `validateLessonContent`. Gemini returns separate `explanation` and `quiz` arrays (every explanation-block field is `required` in the schema, because lite models skip optional ones) and `toContent()` merges them into that array; the validator drops empty-body blocks and cuts questions beyond 5, but still needs a paragraph, an example and 4+ valid questions, and the reason for a rejected output is logged (never sent to the client). `lastError`, `videoQuery` and `attempts` are never sent to the client. `Module.sideQuest` is reserved, `null`, for a later session.
  - Hinglish audio (spec 6, `services/audio*.js`, `hinglishScriptService.js`, `ttsService.js`): `buildAudioSource` turns a ready lesson's blocks into the prompt text (MCQs and `videoQuery` never included); its SHA-256 is the cache key, so `lesson.audio` (`generating` → `ready` | `failed`) stays valid until that text changes, and replays never call Gemini. A job writes the script with `generateJson`, then speaks it with `generateSpeech` in `geminiClient.js` (the Interactions API with `speech_metadata` style annotations, raw 24 kHz L16 PCM; the TTS docs no longer use `generateContent`) in chunks of ≤ 1,800 characters stitched with 400 ms gaps, encodes MP3 in a worker thread (`utils/mp3Worker.js`, `@breezystack/lamejs`) and stores it in the GridFS bucket `lessonAudio`. `services/audioJobs.js` runs jobs in memory (`AUDIO_GEN_CONCURRENCY`, default 1), and the per-user daily limit (429) is counted in memory, so both only work for a single server process. Claiming is an atomic `findOneAndUpdate`; `server.js` marks interrupted jobs `failed` and sweeps orphaned files at boot; `deleteCourse` cancels jobs and deletes the course's files. `fileId`, `sourceHash`, model names and `lastError` are never sent to the client.
  - Module videos (spec 7, `services/moduleVideoService.js`, `videoJobs.js`, `videoLimits.js`, `videoQueryService.js`, `videoRankService.js`, `youtubeClient.js`): `Module.video` is `null` until the first GET claims it atomically and starts a job (`searching` → `ready` | `none` | `failed`); no search runs at course creation, and a GET never restarts `none` or `failed`, only `POST …/retry` does. A job writes a phrase from the outline with `generateJson`, makes one `search.list` call, one `videos.list` call and has Gemini return ordered `approvedIds`; candidates are saved straight after the search and steps resume from what is saved, so Try again never repeats a search that succeeded. `none` allows one Search again (`searchCount < 2`); losing every approved video sets `lostAllVideos`, which reopens one more. A GET on a `ready` video over 7 days old re-checks it in the background and never delays the response. The per-user daily cap (429) and two quota stops (search and details, each until midnight Pacific, both blocking new searches) live in `videoLimits.js`; they and the job runner are in memory, so only work for a single server process. `YOUTUBE_API_KEY` is server-only: never a `VITE_` variable, and axios errors are never logged because their URL contains it. Unapproved candidates, `query`, `searchCount`, `lostAllVideos`, `description`, counts and `lastError` are never sent to the client.
- `client/` — Vite 8 + React 19, JavaScript (JSX, no TypeScript).
  - Landing page styling uses **Tailwind CSS v4** (`@tailwindcss/vite` plugin in `vite.config.js`, `@import "tailwindcss"` in `src/index.css`). The landing page must not change when the dashboard is visited.
  - Dashboard UI: **Chakra UI v3** (not v2; v2 snippets like the `theme` prop, `Modal` and `useToast` don't apply). The system is in `src/theme/system.js` (`preflight: false`, and it neutralises Chakra's default `html` colors). The dashboard palette is defined once, as Tailwind theme values in `@theme static` in `src/index.css` (`--color-app-*`, matching the landing page's warm dark look with an orange accent, olive progress and brick-red brand); `system.js` maps Chakra tokens to those variables with `var(...)`, so don't hard-code hex in dashboard components. `colorPalette="accent"` is a custom Chakra palette built from the accent variable. Headings use the landing page's `--font-heading` with `letterSpacing="tight"`; the sidebar shows the landing page's "AI-Powered Course Generator ✳" wordmark; primary actions use `components/dashboard/PillButton.jsx` (white pill, brand-colored text, → arrow). `ChakraProvider` is mounted only inside `DashboardLayout`, not in `main.jsx`, and the layout puts `.dark` on `<html>` while mounted so portaled menus, dialogs and the drawer are dark too. Toasts use `components/dashboard/toaster.js` + `AppToaster.jsx`. No icon package; icons are inline SVGs in `components/dashboard/icons.jsx`.
  - Chakra gotchas found here: `Field.Root` ignores `ids`, so set `id` instead; the `RadioCard` border and checked state are on `Item`, not `ItemControl`; the `progressbar` role is on `Progress.Track`, so give the label there; `SkipNavLink` takes `id` (its target), not `href`; Menu `onSelect` goes on `Menu.Root` and receives `{ value }`.
  - Routing: `react-router-dom` v7. Auth: `@auth0/auth0-react`, provider in `src/context/Auth0ProviderWithNavigate.jsx` (inside `BrowserRouter`). API calls go through `src/utils/api.js` (`apiRequest`).
  - `html2canvas` + `jspdf` are for exporting generated course content to PDF in the browser.
  - `vite.config.js` proxies `/api` to `http://localhost:5000` in dev.

## Commands

Client (`cd client`):
- `npm run dev` — Vite dev server
- `npm run build` / `npm run preview`
- `npm run lint` — oxlint (not ESLint)

Server (`cd server`):
- `npm run dev` — `node --watch server.js`; `npm run start` — `node server.js`.
- `npm test` runs Vitest (`vitest.config.js` sets dummy env vars). Tests are in `server/tests/`: supertest against `app.js`, `checkJwt` and the Gemini services mocked (`courses.test.js` and `lessons.test.js` also mock `lessonQueue.js`; `lessonQueue.test.js` runs the real queue with a mocked lesson generator; `audio.test.js` runs the real audio jobs and GridFS with `generateJson` / `generateSpeech` mocked; `moduleVideo.test.js` runs the real video jobs with `generateJson` and `youtubeClient.js` mocked; `youtubeClient.test.js` mocks `axios`), Mongo via `mongodb-memory-server` (the first run downloads a `mongod` binary). Single file: `npx vitest run tests/courses.test.js`; single test: add `-t "name"`.
- `nodemon` was removed (it pulled in a `minimatch` advisory); use `node --watch`.
